# RAG Evolution 对抗性审查与优化计划

**目标：** 以独立的产品/UI、后端/安全和端到端运行视角验证当前 Demo；只修复可复现且直接影响正确性、可用性或真实/模拟边界的缺陷。

**约束：** 不读取、输出或提交 `.env`；不主动发起真实模型调用或 40 条真实评测；不新增未经证据支持的功能；所有修复先写失败测试，并由独立审查复核。

## Task 1：对抗性只读审查

- 产品/UI：中文理解性、状态与错误态、无障碍和响应式。
- 后端/安全：请求验证、Provider fallback、状态语义、密钥与成本边界。
- 运行：服务启动、完整测试、构建、浏览器主线与 Console。
- 验证：形成按严重度排序、可复现且带证据的发现清单。

## Task 2：后端真实模式完整性与状态一致性

- 使用严格请求模型：`question` 必须是 1–1000 字符的字符串；`limit` 必须是 1–40 的严格整数。
- 拒绝携带不可信 Origin 的付费 POST；保持无 Origin 的本地 API 客户端兼容。
- Provider 对回答文本和 Judge 分数进行类型、有限性与 0–100 范围验证。
- LIVE 评测只有在回答确为 `live` 时才调用 Judge；fallback 必须计为失败，不能产生 LIVE 分数。
- readiness 区分“已配置未验证 / 可用 / 不可用”。
- 将 Demo Active 版本写入 SQLite 独立状态，并让 `/api/versions` 与 `/api/workspace` 从同一状态源读取。
- 为模拟实验 API 增加机器可读的 `mode=mock` 与 `source=seeded_replay`。
- 每个行为先写失败测试，后写最小实现。

## Task 3：前端可信表达与关键可用性

- Preview 显示单次请求实际的真实/模拟来源、模型、延迟和 fallback 原因；失败时清除旧结果并显示错误。
- 明确原文件不上传，但真实回答会发送问题和相关知识片段给 DeepSeek。
- 添加手机端导航入口、保留模式标识；数据表可横向查看并显示空搜索状态。
- 版本启用后由服务端回读唯一 Active 状态；实验页面标明“模拟重放”。
- 删除假下拉交互，并修正概览“问题案例”跳转到评测。
- 验证：前端测试、构建和浏览器可访问性/响应式复验。

## Task 4：端到端复验与最终审查

- 浏览器覆盖 Overview、Evaluation、Evolution Lab、Versions、Preview、Settings；检查 Console。
- 独立复审本轮 diff，确认没有泄露密钥、伪造真实模式或引入无关重构。
- 验证：`./start.sh` 可启动、API smoke 通过、`git diff --check` 通过。
