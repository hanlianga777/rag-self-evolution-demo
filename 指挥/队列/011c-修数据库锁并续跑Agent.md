# 任务 011c：修“数据库被锁”导致试跑中断，然后续跑 Agent 第一轮（花钱，自动值班）

## 背景（总指挥用只读接口查到的事实）
- 011b 启动的实验 `EXP-20261102214606947837`，方案 A 的 Sandbox `EVAL-20261102214652063044` 在 2026-11-02 21:52 UTC（多伦多 16:52）停在 **7/50**，状态 partial。
- 唯一技术错误：题目 `CSV-20261101100758945425-08`（Q08），阶段 generation，`OperationalError: database is locked`，被归为 `permanent_or_unclassified`、`retryable=false`，于是整轮停下。循环状态 failed，last_error“试跑未完整结束，请检查已保存断点后再处理”。B、C 还是 generated，预算显示 used 0 / 12。
- 出错时间正好是 012b 开始接续（16:50），012b 当时在用浏览器大量打开页面、读 8010 接口；012b 报告还记录了一次 `/api/evaluation?active_task=true&light=false` 返回 500，原因未知，很可能是同一个锁。
- 结论：这不是模型或网络问题，是**后台循环写库时，页面读接口和它抢 SQLite 锁**。面试演示时一定是边开页面边跑 Agent，必须修好。

## 要做的事
开始前确认没有评测、复核或实验在跑（现在循环已停）。改正式库前先备份。**本单可以在续跑之前重启后端；续跑开始后不准再重启。**

### 一、查清楚并修好锁
1. 查根因，报告写清楚：
   - 正式库连接是否开了 WAL、busy_timeout 设了多少；
   - 哪些读接口（尤其 `/api/evaluation?light=false`、`/api/optimization`、`/api/experiments/...`、Baseline / Agent 页面会调的接口）会在读的时候写库、开长事务或长时间持有连接；
   - 后台 Sandbox 写断点时的事务有多长。
   能用后端日志确认 16:52 那次和 500 那次就写出来，确认不了写“未知”。
2. 修：
   - 正式库开 WAL，设置合理的 busy_timeout（例如 30 秒）；
   - 读接口不写库；如果确有必要写（例如缓存），改成短事务，不能挡住后台循环；
   - 后台循环里写库遇到 “database is locked / busy” 按**内部可重试错误**处理：等待后自动重试（例如最多 5 次，逐步加长等待），重试成功就照常继续，过程记进技术详情；重试完仍失败才算技术失败。这类错误不是 Provider 错误，不能标成 permanent。
   - 生成阶段遇到锁时，如果模型回答已经拿到，重试只重写库，**不要重新付费调用模型**。
3. 测试（临时库、Stub，不调 Provider）至少覆盖：
   - 模拟后台循环逐题写断点的同时，并发反复请求上面那些读接口，循环不出错、读接口不返回 500；
   - 人为制造一次锁等待，后台写库能自动重试成功，结论正常；
   - 一直锁住超过重试上限，才记技术失败。

### 二、续跑 Agent 第一轮
1. 重启后端加载新代码。确认：当前 Baseline 仍是 `EVAL-20261102140722852830`、判分 low、实验 `EXP-20261102214606947837` 还在。
2. 用产品现有的“从断点继续”流程续跑方案 A 的 Sandbox：**已完成的 7 题不重跑、不重复付费**，从 Q08 接着跑，跑完 A 后循环照常进入 B、C。
   - 如果产品没有“断点续跑”，或续跑后循环不会自动接着跑 B、C：在报告里写明；按产品现有规则选最省钱的办法让循环继续（例如对同一实验重新调用 `/run-cycle` 并复用已保存断点），不要新建实验、不要让 Agent 重新出方案、不要手工改方案。
   - 这次失败是我们自己的产品故障，**不应该占掉 12 次试跑预算**。续跑后看 evaluation_budget：如果 A 被算了两次，修正为一次，并在报告写明。
3. 确认续跑后又有 2–3 道题正常出结果、没有技术错误，就结束本单。**不要等全部跑完，不要循环轮询。**
