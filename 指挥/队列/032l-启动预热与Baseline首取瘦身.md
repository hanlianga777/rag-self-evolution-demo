# 032l：启动预热与 Baseline 首取瘦身（接 032j 遗留）

**授权**：用户已授权，不需要停下来等确认。

## 背景

032j 后，大部分页面已经很快，剩下两处超过 1 秒：

1. **后端重启后第一次打开首页要 1981 毫秒**。原因是缓存是空的，优化概要接口首次计算要等约 1.8 秒。之后同样打开只要约 140 毫秒。
2. **Baseline 首访最慢 1363 毫秒**。完整报告接口返回约 16.8 MB JSON。另外，页面要先等约 300 毫秒的 Bad Case 列表，才开始请求完整报告，形成串行。

面试演示时，最容易遇到的就是"刚启动就打开首页"。

## 要做的事

1. **启动后后台预热**：后端启动完成、开始监听之后，在后台线程依次调用首页和八个一级页面首屏需要的只读接口，把读取缓存填好。
   - 预热不能阻塞启动和健康响应；
   - 有活动评测时跳过对应接口；
   - 预热失败只写本机日志，不影响服务；
   - 预热只读，不调用模型，不写库。
2. **Baseline 首取瘦身**：
   - 首屏需要的门槛、按题型答对、Bad Case 列表、检索与用量，先用一个**只读概要**一次取齐；
   - 逐题的完整回答、检索路径、证据原文这类大字段，在打开抽屉时按题号再取，接口已有的话复用；
   - 消除"先等 Bad Case 列表、再取完整报告"的串行。
   - 页面上能看到的内容和改动前完全一样，抽屉内容也不能少。
3. 原有完整报告接口保留，供"完整报告 / 导出"等需要全部数据的地方使用。

## 目标与验收

- **重启后端后**，1440×900 新浏览器上下文：
  - 首页冷启动连续 5 次都低于 1 秒，**包括重启后的第一次**；
  - Baseline 首访连续 5 次都低于 1 秒。

  预热需要时间，所以计时从"后端监听端口 + 预热完成"开始算。报告里另外写出从进程启动到预热完成用了多久。
- 达不到就如实写差距和原因，不挑最快的报。
- Baseline 页面和每类抽屉，改动前后各截图对比，内容一致。新增测试覆盖：
  - 概要与完整报告的一致性；
  - 抽屉按需取数的正确性；
  - 有活动评测时跳过预热。
- 后端定向测试、前端全量测试、`npm run build` 都通过，不删测试、不加 skip。
- 正式数据库 33 张表、17 个索引文件、运行设置前后不变。
- 需要重启后端就用原 supervisor 重启，确认无人值守和平价设置不变。
- 收尾确认 5174 提供的是最新构建。
