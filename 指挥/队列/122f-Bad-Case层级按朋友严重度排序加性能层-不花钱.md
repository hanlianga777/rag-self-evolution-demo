# 122f Bad Case 层级：按朋友的严重度排序，并加入性能层（ST-06，不花钱）

依据：用户 11-26 08:20 拍板：「按照朋友推荐的层级来，学习它里面的逻辑」；互审 38 第 6 节「Bad Case 地图」。前置：122e 完成。

## 规则（写进 `rules.py`，测试同步检查）

1. **故障分为四层**：检索、生成、安全、性能。`LAYERS` 加入 `performance`；`layer_signals()` 不再排除延迟门槛（`agent_round_contract.py` 约第 240 行）。

2. **每道错题按朋友的五类定严重度**，按错误类型固定，Agent 不能改：

   | 朋友的类别 | 我们的判定依据 | 严重度 |
   |---|---|---|
   | 检索失败（查不到） | 标准证据没进入候选池（recall） | 致命 |
   | 延迟高 | P50 或 P99 门槛没过 | 致命 |
   | 检索噪声 / 方向错（查到错的） | 证据在候选池里，但排序靠后，或没进 Final（ranking、final） | 严重 |
   | 模型过度拒答（该答没答） | 资料已给到，回答却说「资料不足」或拒答（over_refuse） | 中等 |
   | 安全边界误伤 | 负向题中的误伤：本该追问或说明，却直接拒答；或格式不当 | 轻微 |

   **朋友的表里没有的两类，总指挥补充如下**（报告里要单独列出，交用户确认）：
   - **生成层答错或漏要点**（资料给到了，但答错、漏点、编造）：归为「中等」，理由是与「该答没答」同属生成环节；
   - **严重安全违规**（该拒没拒、被注入绕过）：会直接让安全门槛（≥95%）不过，按第 3 条第 1 步「门槛优先」处理，同样排在最前面。

3. **目标层排序**：
   1. 有 Hard Gate 没过时，优先处理导致门槛失败的那一层，包括安全门槛和延迟门槛；
   2. 门槛都过了，按各层错题里的最高严重度排：致命 > 严重 > 中等 > 轻微；
   3. 严重度相同时，错题数多的层优先；
   4. 错题数也相同时，上游优先，顺序为检索 → 生成 → 安全 → 性能；
   5. 当前层已没有可调的机会时，转到下一层。

4. **性能层的可调动作**：
   - thinking 降档；
   - 关掉 multi_query、hyde、query_decompose；
   - 缩小 candidate_k 或 top_k；
   - 缩小 retrieval_max_tokens。

   性能变好、但出现新增错题的方案，不能晋升。
5. **50 题全对、但 P99 超标时**，不结束实验，而是启动性能层优化。

## 单测（决策测试，用临时数据，不调用模型）

| 场景 | 应选的层 |
|---|---|
| 检索失败 1 道 + 生成漏点 3 道 | 检索（致命 > 中等） |
| 检索噪声 3 道 + 检索失败 0 道 + 生成 3 道 | 检索（严重 > 中等） |
| 50/50 全对但 P99 70 秒 | 性能 |
| 安全门槛没过 + 检索失败 2 道 | 安全（门槛优先） |
| 生成 2 道 + 过度拒答 2 道，都是中等 | 生成（同严重度、同数量，按上游顺序） |
| 性能改善但新增 1 道错题 | 不晋升 |
