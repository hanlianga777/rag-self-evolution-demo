## 总指挥查到的根因（务必先读）

1. **思考模式下 temperature 不生效。** `backend/app/providers.py` 的 `_request` 只在 thinking 为 disabled 时才发送 temperature。而 `DEFAULT_TASK_THINKING` 里，生成（baseline / generation / candidate / answer 为 max）、Judge（low）、HyDE（high）、Query Rewrite / Multi-Query（low）、auxiliary（high）全部开着思考，所以**这些调用全部是随机采样**。
2. **实测证据**：
   - D 与 R3-B 配置完全相同，50 道题的回答没有一道逐字相同；4 道题判定翻转，其中 3 道检索结果完全相同。
   - "分级回答 + High"的 8 次评测分别答对 44 / 46 / 48 / 45 / 45 / 47 / 47 / 48 题，有 13 道题时对时错。
   - HyDE 开启时，同配置两次只有 18 道题的检索结果相同。
3. **Agent 把噪声当成了因果。** R3-C 的"最低相关度 0.1"实际一个片段都没过滤掉，检索结果与 R1-A 完全相同，Agent 却把它新错的 Q05、Q36 归因到这个参数上。Agent 拿不到"这道题的检索有没有变"这类逐题证据。
4. 朋友的方案用的是同一套调节项，他们最终的方案 D 也关掉了深度思考。


## 第零部分（用户 11-15 10:19 追加，优先于下文）：可调参数只保留朋友方案里有的

用户原话："pipeline 配置是不是每一条我们朋友都有？特别是 prompt 策略'完整性优先''分级优先'这些，我不希望我们自己去原创。"

- 检索前：Query Rewrite HyDE、Multi-Query Expansion（3 个变体）、Query Decompose；
- 检索：TopK（4–6）、MinScore（默认 0.4）、MaxTokens、检索策略（语义 / 关键词 / 混合，以及语义与关键词权重）；
- 检索后：Rerank 开或关；
- 生成：一份固定的 Prompt 模板、模型、深度思考档位。

我们方案里属于**原创、朋友没有**的，一律从 Agent 可调范围里移除：

1. `prompt_strategy` 的 Grounded / Completeness / Tiered / Abstention 四种策略全部移除，Agent 不再调 Prompt。生成提示词固定为**朋友的默认 Prompt 模板**，只把领域换成机器人说明书，保留我们现有的引用编号与安全边界约束（`generation_boundary`），不另加规则：

   > 你是一名专业的机器人说明书客服助手。请严格根据提供的说明书上下文回答用户问题。
   > 1. 使用通俗的口语化语言；
   > 2. 清晰列出操作步骤，直接告诉用户怎么做；
   > 3. 针对故障提供处理流程及安全提示；
   > 4. 不得编造说明书以外的信息；
   > 5. 【关键】禁止引导用户翻书查页码：若参考内容里出现"请参见……（页码）""详见某章节"，而该部分的具体说明也在参考内容中，就直接提取关键操作步骤呈现，不要提页码；若具体操作不在参考内容中，就礼貌告知"建议联系售后处理"，不要说"请查看手册第 X 页"；
   > 6. 【关键】安全警告必须保留：参考内容中的"切勿自行修理""⚠"等安全提示，需在回答中体现。

2. `candidate_k`（重排前的候选池大小）不再可调，固定为 12。
3. `rerank` 只保留 开 / 关，移除我们自己发明的 `query_only`（"仅按原问题排序"）。
4. `query_rewrite` 不再作为单独参数，朋友把它和 HyDE 写在同一项，保留 `hyde`。
5. `multi_query` 只保留 关 / 3（朋友用的是 3 个变体）。
6. `generation_thinking` 按第一部分固定为关闭。

保留可调的参数：`top_k`（4 / 5 / 6）、`min_score`（0 / 0.2 / 0.3 / 0.4）、`hybrid_search`、`hybrid_alpha`（0.2 / 0.3 / 0.5 / 0.7 / 0.8）、`rerank`（开 / 关）、`hyde`、`multi_query`（关 / 3）、`retrieval_max_tokens`。

另外，在报告里逐项证明每个保留参数都**真实生效**，不是只改了配置值：

## 第一部分：根治随机性（代码）

1. **生成回答**（Baseline、Candidate、D、问答验证的同一条生成链路）：
   - 思考一律关闭，temperature = 0；
   - Provider 支持 seed 的就固定 seed，不支持的在报告里写明；
   - `generation_thinking` 从 Agent 可调参数里移除，只允许 off；
   - 页面上与"思考档位"有关的说明以后另单处理，本单只保证后端一致；
   - 旧记录里的 thinking 值原样保留，不改历史数据。
2. **检索阶段的模型调用**（HyDE、Query Rewrite、Multi-Query、Query Decompose 等）：思考关闭，temperature = 0，能固定 seed 就固定。
3. **Judge**：思考关闭，temperature = 0，能固定 seed 就固定。放开 `judge_thinking` 的校验，允许 off，并把 off 设为默认值。
4. 确认没有其他漏网的随机来源：
   - 检索排序的并列顺序要稳定；
   - 集合 / 字典遍历顺序不能影响上下文拼接顺序；
   - 并发返回的顺序不能影响结果。

   发现的都修掉，并在报告里列出。
5. **一次性验证修复是否生效**（只做这一次，用于证明根因已除，**不是评测时一道题跑多次**）：
   - **Judge 校准**：用新的 Judge 设置，对一份已完成评测（R1-A，`EVAL-20261114175201544865`）里**已保存的 50 个回答**重新判分，不重新生成回答，与原判定对比一致率。≥ 90% 继续；低于 90% 就停下，写清原因和不一致的题，不进入第二部分。
   - **确定性抽检**：任选 3 道题（含 1 道负向题），用新的 Baseline 配置各生成并判分 2 次。回答逐字相同、判定相同才算通过；不通过就继续查原因，不进入第二部分。
   - 两项验证的调用次数、token 数和费用都写进报告。
6. 后端测试：思考关闭时 temperature 必然发送，Judge 允许 off，检索阶段调用参数正确，排序稳定。用替身 Provider。

## 第二部分：让 Agent 真正"根据上一轮分析"

1. **逐题对比交给 Agent**：每轮规划前，程序先算出逐题对比，作为结构化输入交给 Agent。
   - 对比对象：当前最好方案和 Baseline；
   - 每题标记：修好 / 新错 / 仍错；
   - 每题附带：检索结果（交给模型的证据）有没有变、判分缺了哪条必答要点。
2. **归因规则**写进提示词，并由程序校验：
   - 某题检索结果没变，就不许把它的变化归因到检索类参数；
   - 每个 Candidate 相对它的基础方案，最多改 2 个参数；
   - A / B / C 方向互不相同；
   - 配置与已评测过的方案完全相同的，直接复用结果，不重复付费。
3. **事先预测**：每个 Candidate 运行前保存——要改的参数及原因（引用逐题证据）、预计修好的题、风险题。
4. **事后对账**：运行后保存每轮结论——
   - 修好 / 新错 / 仍错，每题一句原因；
   - 参数判断：有效 / 无效 / 不确定，附证据；
   - 带入下一轮的经验。

   下一轮规划必须读取上一轮结论。
5. 输出全部用中文业务短句，参数用中文名，题号写成 Q29 形式，**不出现内部编号或英文 snake_case**，方便页面直接展示。
