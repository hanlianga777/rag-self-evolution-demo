# 根因复盘：为什么一直在返工，以及这次修了什么（2026-11-16）

> 依据：仓库 1,094 次提交、159 张历史任务单、`035-逐题对比.csv`、047/049 报告；两个朋友压缩包共 56 张截图逐张看过。

## 一、先说结论

1. **最本质的原因只有一个：我们一直在测一个比测量误差还小的差别。** 同一套配置跑两遍，50 道题里就有 2–3 道对错会变；而 11-16 的 Max Baseline 只错了 2 道，Agent 最多只能修 2 道，合格规则又要求"净少 1 道、新增不超过 1 道"。信号不大于噪声，Agent 合不合格基本靠运气。之前反复改 Judge 档位、Baseline 档位、合格规则，本质上都是在想办法赢一次掷硬币，所以怎么改都会再出问题。
2. **第二个原因：花钱之前没有一个便宜的"这次能不能看出效果"的检查。** 每次都是先跑完 Baseline 和 Agent，花了时间和钱，才发现没有改进空间。其实 Agent 能调的几乎全是检索参数，检索结果是确定的、几分钱就能算出来，本来可以先算。
3. 其余的 bug 和返工，大多能归到五个共性问题：规则跟着单次结果改；同一条规则散在六个地方；总指挥写的代码没跑就发；实验结果还没定就打磨前端；同一时间有两个总指挥会话在改同一个仓库。

## 三、七个共性根因（按影响排序）

### 根因 1：信号小于噪声（最本质）

- 11-16 Max Baseline 错 2 道（Q21、Q30，都是"不够完整"，属于生成层），最大可改进量 = 2，同配置噪声 = 2–3。
- 11-15 那次 Baseline 错 8 道，但多数是安全题。Agent 能调的是检索参数，修不了这类题：Q38 在 10 个方案里一次都没修好。
- **朋友为什么没遇到**：题卷里专门放了"检索难"的消融题（口语、缩写、别名、跨领域）。扣子案例 18 道消融题里有 11 道一段资料都没检索到，Baseline 消融正确性 57.8%、完整性 34.4%，门槛不过；Agent 开多路查询、加大 TopK 后补回来，D 方案消融正确性升到 74.4%，10/10 过线。改进量是十几分，远大于噪声。另外，朋友判合格看的是平均分门槛，Colin 再加一道"逐题不回退"，都不是"错题净少 1 道"。
- 推论：我们对齐了朋友的字段、门槛和页面，却没对齐最关键的那条机制。

### 根因 2：花钱前没有便宜的"能不能成"检查

- 所有判断都在付费运行之后：11-16 加的"Baseline 错题 ≥5 才启动 Agent"也要先花钱跑完 Max Baseline，而且不区分这些错题 Agent 能不能修。
- 检索是确定的：同一个问题、同一套检索参数，进最终资料的切块每次都一样，成本几分钱。可以在付费前就算出"Baseline 配置下哪些题的证据没进最终资料、换哪组参数能补回来"。

### 根因 3：规则跟着单次结果改

- Judge 档位五次、Baseline 档位四次、合格规则和 D 规则多次修改，几乎每次都由上一轮的结果触发。
- 改完要重跑，重跑又带来新的随机波动，于是再改。这是一个自我强化的循环。

### 根因 4：同一条规则有六个"真相来源"

- 规则总表、任务单、HANDOFF、SPEC、`.env`、代码常量，冲突时靠一个优先级顺序人工判断。
- 实例：`.env` 的 `BASELINE_THINKING=off`；评分要点从判分里删了，但质检和页面还在用；判分量纲改了，前端没跟（047）；复用键漏了证据身份（033e）。

### 根因 5：写了不跑，验的不是要跑的那条路径

- 总指挥写的代码自己没跑就交给 Codex，Codex 在 Mac 上发现基本错误，一来一回 30–60 分钟，还会触发两次重试和暂缓。
- 实例：049 发出前写着"总指挥已在本地逐题跑过，50 题 0 错"，但验的是另写的 CSV 读法；正式导入脚本用 `splitlines()` 吃掉了单元格换行，到 Codex 那里 19 题报错。
- 这个云端环境其实能跑 1,000 多个后端测试，"跑不了"不成立。
- 也说明 11-16 把"Codex 写代码能力弱"当成原因、改由总指挥写代码，并没有打中要害：今天两个卡点（CSV 读法、判分量纲）都出在总指挥写的代码里。问题在"没跑"，不在"谁写"。

### 根因 6：表现层先于实质

- 实验结果还没定，前端已经改了 60 多张单。每次数据一变，页面要重查；032 整体改版又整体退回。
- 测试里还有依赖真实时钟的用例（走到"等高峰结束"会真的睡几个小时），同一份代码早上和晚上跑结果不同。

### 根因 7：同一时间有两个总指挥在改同一个仓库

- 这次复盘进行中就发生了一次：本会话在查 049 的 CSV 读法 bug 时，另一个总指挥会话在 19:54 独立修了同一个 bug、改了参考答案并恢复 049；20:11 049 又因 Q14 第三、四次失败，20:21 修 Q14 后 20:26 重新开跑。同一个 bug 被修两遍，而"发出去才发现"又重演了一次。
- 规则：同一时间只允许一个会话往 `指挥/队列/` 发单、往 main 推代码。其他会话的改动走单独分支，由当班总指挥合并。本次复盘的修改就放在分支 `claude/root-cause-fixes-20261116`，没有动 main 和队列。

## 四、问题定义本身对不对（回应你的第 2 点）

**你说的"很多问题没解决、要从头再来"，是症状。** 底层只有一个问题：实验的设计让 Agent 不可能稳定地赢。前面每个"问题"（判分不稳、Agent 不合格、门槛太敏感、题卷太简单）都是它在不同地方的表现。

**几处把手段当成了目标：**

1. **"严格对齐朋友"不是目标。** 目标是面试时每个设计都能讲出"为什么"。面试官问"为什么这样设计"，"因为朋友这样做"是最弱的回答。而且我们在朋友的框架上加了朋友没有的最严规则（净少 1 道、新增不超过 1 道、每个方案最多改 2 个参数），反而让合格更依赖运气。
2. **"Agent 必须合格"不是目标。** 目标是讲清一个可信的闭环和你的判断力。这一个月的弯路本身就是很好的面试素材："我发现同一配置跑两遍会有 2–3 道题翻转，于是先测噪声，再按行业做法设计题卷让信号远大于噪声，并在花钱前加了确定性的可修空间检查。"这正是 AI 解决方案岗最想听的评测严谨性。
3. **"前端像素级打磨"不是目标。** 页面服务于讲故事；实验结果没定，打磨就会反复作废。
4. **"全自动无人值守"不是目标。** 整场实验只花 4–5 美元，避开高峰价省下的是几毛钱，却多次让实验多等几个小时。你今晚取消高峰限制是对的。

**更值得解决的问题**：先确认"信号"存在再花钱；把剩下的精力从 UI 转到讲稿和问答准备。

## 六、用户拍板结果（2026-11-16 21:26）

1. **不把"检索可修空间 ≥5 道"作为启动条件。** 理由：Bad Case 有生成、检索、安全边界、性能四类，Agent 会按实际情况选方向（例如调思考档位），不能只盯检索。扫描保留，只作检索层的参考信息；开跑前把四类 Bad Case 和 Agent 可能的修复方向写进报告。启动 Agent 仍按原规则：Baseline 错题 ≥5 道。
