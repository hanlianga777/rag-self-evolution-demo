## 1. 这几天讨论了什么、定了什么

### 1.1 协作方式
- 分工：Claude 只做总指挥，负责定方向、写任务单、验收；Codex 写代码、跑任务；用户拍板。
- 两种执行方式：
  - **手动**：用户把固定的一句话发给 Codex，让它读 `指挥/当前任务.md`；
  - **值班**：任务单放进 `指挥/队列/`，由值班脚本依次交给 Codex，加 `--一直跑` 就不按钟点收工。

- 成本原则：DeepSeek 只在平价时段跑。高峰时段是多伦多工作日 20:00–23:00、01:00–05:00。产品里加了"只在平价时段运行"开关，默认开启。

### 2.2 两个被排除的猜测
- **"判分档位太低导致误判"**：同一批回答，max 档判分和 low 档判分只差 1 题；之前的校准也是 50 题里 49 题一致。所以不是判分档位的问题。
- **"DeepSeek 降智了"**：11-01 和 11-03 两次 max 档，模型名相同，平均思考量 2333 对 2223 个 token，平均耗时 18.5 对 17.6 秒。看不出降智的证据。

### 2.3 找到的真正原因：评分偏严 + 负向题波动
- 判题规则：每题有 1–3 条"必答"，全部答到才算对；"加分"项缺了不扣分；答出"禁止项"直接判错。
- 逐题检查后发现，大部分错题是真错，多数是检索没找到证据。但 Q35、Q37、Q46 这三道负向题属于偏严：**该做的动作（拒绝或追问）已经做了，只是第 2 条必答里的某个细节没说全**。模型每次的措辞不同，所以这三道题的对错时有时无，而它们恰好决定了安全门槛能不能过（负向题只有 20 道，门槛 95%，最多只能错 1 道）。
- 处理方法：先试跑，再正式改。
  1. 定统一原则：负向题的必答 = 正确行为 + 最多 1 个核心要素；正向和消融题里，用户直接问到的步骤全部必答；解释性的话移到加分。按这个原则复核 50 题，改了 20 题。
  2. **只重新判分，不重新生成回答**：拿已保存的回答，用新要点重新打分。这样看到的差别只来自评分标准，不混入回答本身的随机性，也省钱省时。
  3. 设好成功标准：三道题至少 5/6 一致；不放过真错的题。试跑结果达标。
  4. 结果：今天 max 档的回答按新要点算，**44/50，11 项门槛全过**（原来 42/50、9/11）。有 3 份旧回答的 Q38 从对变成了错，这符合原则，保留不改。
- 同时试了"关闭思考 + 随机度 0"：速度快了 40–70%，但同一题两次的回答文字仍然不同，有一题判分前后不一致，质量也没有稳定超过 high 档。所以**不作为默认**，只保留为 Agent 可选的档位。

## 4. 面试怎么讲

### 4.1 主线（20–30 分钟）
一句话：**"评测负责发现问题，Bad Case 分类负责定位问题，配置表负责承接优化动作。"**（朋友 2）

按页面顺序讲：
1. **概览**（1 分钟）：要解决的问题——企业 RAG 交付靠人工调参，效果不稳定、不可回归。目标是"自动评测 → 自动优化 → 人工确认发布"的闭环。
2. **知识库 + Pipeline**（3 分钟）：父子分块，小块负责找得准，大块负责答得全；12 个可调参数，每个都对应一类问题。
3. **Golden Dataset**（4 分钟）：正向 20、消融 10、负向 20（证据不足、需要追问、安全关键、提示注入）。程序硬校验 + Probe/QC，人只看红线；冻结后才评测；评分标准改了就建新版本，旧版本保留。
4. **Baseline**（4 分钟）：11 项门槛、逐题判分、4 大类归因、耗时拆解。**在这里埋下伏笔**："我先把算力拉满（max 档），看这套系统的上限……"
5. **Agent 工作台**（8 分钟，重点）：Agent 只拿客观事实；A/B/C 三个方向，强制一套效率方案；三套之间参数互斥，保证每个改动都能归因；Sandbox 隔离试跑；回归检查。**在这里揭晓伏笔**：max 档质量够，但 P99 超标；降档 + 检索补偿既能提速又能保质量。
6. **方案 D、推荐、发布**（4 分钟）：D 组合有效改动；发布要求零新增错题，否则保留赢家；可以回滚。
7. **问答验证**（2 分钟）：同一个问题，对比发布前后的回答。

### 4.2 设计巧思清单（可以主动讲）
1. **先拉满再降档**（用户本人的设计）：用 max 档证明上限，再让 Agent 用数据决定能不能降。不管结果如何都有故事：降不了，说明 max 有必要；降得了，说明在质量不变的情况下省了一半时间和成本。
2. **单变量实验 + 组合优化**：A/B/C 每套只测一个思路，D 负责组合。第一次 C 混了 3 个参数、说不清谁弄坏了题，就是反面教材。
3. **修好 A 不搞坏 B**：回归检查；安全关键和提示注入题零新坏；发布要求零新增错题。
4. **成本意识**：12 次试跑预算、高峰时段自动暂停、每题费用可见、判分档位经过校准后用 low。
5. **评分标准治理**：发现偏严，先定原则、再小规模试跑、最后正式采用；**只重新判分、不重新生成回答**，把评分变化和回答的随机性分开。
6. **工程可靠性**：断点续跑、重启后自动接上、被规则拒绝后自动带原因重出。

### 4.3 可能被追问的问题
- **"大模型每次回答不一样，你怎么保证评测可信？"**：开着思考模式时，随机度没法固定（这是 DeepSeek 官方的规定）。我们做了三件事：评分要点只卡核心行为，不卡措辞；评分标准改动前先做试跑；判分档位用校准数据选定。还要坦白说明：负向题样本少，门槛很敏感，这是我们正视的真实难点。
- **"为什么不让 Agent 直接一次改很多参数？"**：那样改坏了说不清是哪个参数的原因，下一轮也没法学习。先做单变量，再由 D 组合。
- **"为什么判分用 low 档？"**：校准显示 low、high、max 三个档位判同一批回答，50 题里 49 题一致；low 便宜又快。
- **"Agent 和人工调参有什么区别？"**：Agent 读的是逐题事实和有害改动清单，提出可验证的假设，并受规则约束；人只在发布前确认。

## 5. 我（Claude）的想法
