# 121 前端 UI 改造：共同规范（121a～121g 每张单都必须遵守）

- 依据：互审 52（Claude 与 GPT 合议）。用户 11-25 拍板：保留深色导航；拆成 7 张小单顺序执行；概览页现有版式是用户最喜欢的，只修对齐和多余内容；任务单先存着，用户说"改 UI"时再请示执行。
- 状态：**存放在 `指挥/待排/`，不在队列里**。等用户同意后，总指挥按顺序一次只放一张到 `指挥/队列/`。

## 一、视觉基准

1. **以「RAG 自进化概览」页现有版式为全站视觉基准**：大数字加对比、卡片分区、配色和留白，其他页面向它靠拢。不要另起一套风格。
2. **保留深色左侧导航**，导航项按三组分开：

   ```
   RAG 自进化概览
   ── 准备 ──        知识库 / Golden Dataset / Pipeline 配置
   ── 评测与优化 ──  Baseline / Agent 工作台
   ── 发布与验证 ──  发布 / 问答验证
   ```

   - 分组标题用小号浅灰字；
   - 路由、hash、页面顺序不变。
3. **问答验证的 Before/After 结构保留**：
   - 左列题目、右侧双列对比；
   - 要点数、引用来源；
   - 「这道题为什么变好」三步链。

## 二、设计 Token（唯一来源：`frontend/src/ui/tokens.css`）

先从概览页现有样式中提取颜色、字号、圆角、阴影，写成 CSS 变量；其他页面只能引用变量，不再写死颜色值。

| 类别 | 规范 |
|---|---|
| 字号 | 页标题 24、区块标题 18、卡片标题 16、正文与表格 14、字段名 13、辅助说明 12～13、KPI 数字 32～40 |
| 数字 | 使用等宽数字 |
| 间距 | 4 的倍数；页边距 24；卡片内边距 20；模块间距 16～24 |
| 圆角 | 卡片 10、控件 6 |
| 抽屉 | 宽 800px，窄屏自适应。头部固定，正文单层滚动，**禁止抽屉内再套滚动框** |
| 状态色 | 只表达语义：成功（答对 / 合格 / 已发布）、失败（答错 / 不合格）、警示（风险）、中性（未运行 / 未晋升）、进行中。检索层、生成层这类分类不使用状态色 |

## 三、数据表达规则

1. **空值**：
   - 0 显示为 0；
   - 没有记录显示「—」；
   - 不适用显示「不适用」；
   - 尚未运行显示「未运行」；
   - 历史版本没存该字段时，只在详情里注明「该版本未记录」。
   - **整列都为空的列直接隐藏**；
   - 禁止把「X → 未知」当作参数变化展示；
   - 禁止为了消灭空值而补 0 或猜默认值。
2. **数字**：
   - 答对显示 48/50；正确率显示 96.0%；提升显示「+3 题」；延迟显示「4.3 秒」；Token 用千分位。
   - 费用非零时保留足够的有效位，例如「¥0.0032（估算）」，**禁止显示「¥0.00」**。
3. **长文本**：
   - 文档名用「短名 + 页码」，完整名放进详情或 title 属性；
   - 列表中的题目最多显示 2 行；
   - **禁止使用超大黑色 Tooltip**，长内容改为点击展开。
4. **内容渲染**：
   - 答案和原文统一走一个安全渲染组件；
   - 支持段落、列表、`sup` / `sub`、表格；
   - 解析不了的表格按原文显示；
   - 不得用正则删掉符号，也不得改动原文的含义。
5. **标签只用于 4 类**：
   - 评测结果：答对、答错；
   - 方案资格：合格、不合格；
   - 工作流状态：未运行、评测中、已完成；
   - 决策状态：已推荐、未晋升、待发布、已发布。

   题型、参数、ID、规则版本一律用普通文字。

## 四、全站禁用文案（分阶段清零，范围见本节末尾）

| 禁用文案 | 理由与替代 |
|---|---|
| 人工保留 | E5 的 A 一律写「第 1 轮 A（Agent 提出）」；沿用来源只在 Candidate 抽屉的技术记录里写「沿用自 E4 第 1 轮评测（用户授权，未重跑）」 |
| 不稳定、波动 | 3 次复核的明细只放在抽屉的折叠区，用「3 次判定：对 / 对 / 错 → 多数为对」这样的写法 |
| Stepwise、Grounded、TableCheck、Thinking Max | 这些选项已在 11-24 删除。`display.ts` 和 `PipelineFields.tsx` 里的残留要清掉；如果后端的可选值列表里也有，写进报告，不要擅自改后端 |
| 设计巧思、研发过程备注类文字 | 改为「优化依据」，或者直接删除 |

**清零范围**：
- 121a～121f：本单负责的页面必须清零，其他位置只登记到报告里；
- 121g：全站现行的业务界面必须清零；
- 历史实验的原始记录、原始回答、测试用例和类型定义中出现这些词不算违规，不得为了清零而篡改历史事实；
- Thinking Max 的口径是「本系统 Agent 不使用」，不要写成「模型不支持」。

## 四之二、定稿补充（GPT 二审采纳，11-25）

1. **三次判定的写法**按实际记录选：
   - 有 3 份有效样本：「3 次判定：错 / 错 / 对 → 多数为错」
   - 只有 1 份样本：「1 次判定：对」
   - 触发安全规则：「3 次判定：对 / 对 / 错；触发安全规则，最终判错」
   - 历史版本没有复核明细：「该版本未记录复核明细」

   「3 次回答复核」和「每份回答内部的 Judge 判分」是两件事，不能混写。展示的回答原文必须和旁边的判分来自同一份样本。

2. **沿用来源要动态读取**：只有存在 `source_experiment_id` 等来源字段时，才显示「方案来源 E4 第 1 轮 Agent 提案｜评测来源 E4 原始 Sandbox｜本实验 经用户授权沿用，未重新评测」。不能因为编号是 R1-A 就写「沿用」。

3. **空值的边界**：
   - 只有非关键辅助列，在整列为空时才隐藏；
   - 正式评测的必要字段缺失时，必须提示「结果不完整」；
   - 「—」不能用来掩盖评测失败或身份不一致；
   - 真实的零费用照常显示为 ¥0.00。

4. **数字一律动态读取**：文中出现的 45/50、Bad Case 5、新增错题 0 都只是当前样例。

5. **状态**：
   - 决策状态分为：未晋升 / 已推荐待审批 / 已审批待发布 / 已发布；
   - 工作流状态补充：已暂停、执行失败、已跳过；
   - 「当前线上版本」「当前实验 Winner」「最终推荐」各自绑定自己的身份，不得把推荐方案的成绩显示成线上成绩。

6. **参数中文主名（定稿，写进 `terms.ts`）**：

   | 代码名 | 中文主名 | 代码名 | 中文主名 |
   |---|---|---|---|
   | candidate_k | 候选召回数 | query_rewrite | 问题改写 |
   | top_k | 最终保留数 | multi_query | 多路查询 |
   | min_score | 最低相关分 | query_decompose | 问题拆解 |
   | hybrid_search | 混合检索 | hyde | 假设文档检索（HyDE） |
   | hybrid_alpha | 混合检索权重 | retrieval_max_tokens | 资料长度上限 |
   | rerank | 证据重排 | generation_thinking | 思考档位 |
   | prompt_strategy | 回答策略 | temperature | 生成温度 |

   - Pipeline 页和技术详情：中文名后带代码名；
   - 卡片、概览、发布摘要：只显示中文名；
   - `hybrid_alpha` 的说明要写清：权重变大时偏向哪种检索，以代码实现为准。

7. **8 页页头职责句（定稿）**：

   | 页面 | 页头职责句 |
   |---|---|
   | 概览 | 查看优化成果、进化过程与当前线上版本。 |
   | 知识库 | 管理知识文档、索引及原文证据。 |
   | Golden Dataset | 构建并管理用于质量评测的标准测试集。 |
   | Pipeline 配置 | 查看系统技术选型与可调参数。 |
   | Baseline | 评估初始回答质量并定位错误根因。 |
   | Agent 工作台 | 根据评测问题探索、验证并推荐优化方案。 |
   | 发布 | 核验推荐方案并管理线上版本。 |
   | 问答验证 | 对比优化前后回答，验证线上实际效果。 |

8. **滚动**：
   - 抽屉内禁止嵌套纵向滚动；
   - 宽表格可以有必要的横向滚动；
   - 不能为了消除滚动而缩小字号或截断证据。

9. **截图验收**：
   - 主视口 1440×812（用户 MacBook 的 Chrome），1280×800 只抽查；
   - 截图使用真实保存的记录；
   - 没出现过的状态，用隔离的测试数据在单测里验证；
   - 不改正式库；发布、回滚、实时问答这类写操作只在测试里验证，不在正式环境点确认。

10. **顺序**：每张单都以前一张单通过总指挥验收为前提；121a 还要求 E5 已经完成、用户已经放行。

## 五、硬约束

1. **只改 `frontend/`**：
   - 不改后端业务规则；
   - 不改数据库；
   - 不调用 DeepSeek 或阿里云；
   - 不重跑任何评测。
2. **数据真实**：
   - 所有数字、题号、状态都来自现有接口；
   - 禁止硬编码成绩；
   - 禁止为了截图造假数据；
   - 失败的方案和真实回退照常显示。
3. **保留现有交互**：
   - 抽屉的焦点恢复、Esc 关闭、未保存修改确认；
   - 引用跳转到知识库；
   - 实时问答；
   - 发布与回滚的确认弹窗。
4. **测试**：
   - `npm run build` 和 `npm test` 全部通过；
   - 旧文案断言随改动更新，**不能为了通过而删测试**；
   - 新组件要有单测。
5. **单子范围**：
   - 只做本单写明的页面；
   - 发现其他页面的问题，写进报告的「留给后续单」；
   - 不顺手改别的页面。
6. **提交**：
   - 不提交截图、日志、数据库；
   - 提交说明以 `(No SPEC Change)` 结尾。

## 六、报告格式（`指挥/报告/121x.md`）

1. 第一行写：`121x：完成 n/n 项；build/test 通过；禁用文案 0 处；留给后续 k 条`。
2. 列出改动文件清单。
3. 逐项写「改了什么 / 怎么自查的」。
4. 附上禁用文案 grep 的输出。
5. 截图只在本机自查，不提交。总指挥会在用户的 Chrome 里逐页逐抽屉验收，验收不过就发修复单，修好之前不放下一张。
