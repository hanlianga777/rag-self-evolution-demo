# UI 全面审核与优化（Codex 任务单草稿 v2，总指挥 2026-11-20 起草，已采纳 GPT 二审意见）

> **状态**：草稿，**不放进队列**。用户 09:18 要求：全部 Agent 候选跑完、发布之前，由用户说开始时再交给 Codex。
> 放行时拆成 3 张单：UI-01、UI-02、UI-03。**UI-01 的审计报告要先经过 Claude 审核、GPT 二审，然后才能放行 UI-02。**
> **性质**：只改前端展示和文案，不改数据、判分、规则和后端逻辑（为了显示需要，可以在接口里补展示字段）。不调用付费接口。
>
> **硬约束**：审批状态、推荐结果、证据可信度、发布状态、版本身份，这几类内容只要出现在页面上，**都必须从正式保存的数据推导出来**。不准为了演示写死结论，不准伪造一个已经闭环的流程。页面上不准写死数字。

## 0. 目标

面试官打开 demo，3 分钟内能看懂下面这条故事线。要分清哪些是自动评测、哪些是人工确认、哪些是正式发布，**不能让人误以为系统会自己发布**。

1. 知识库
2. 黄金测试集，经人工"题卷确认（Gate 1）"后冻结
3. Baseline 诊断：测出错题并归因
4. Agent 提出 A/B/C 方案
5. 沙盒评测与回归对比
6. 人工"报告确认（Gate 2）"
7. 合并方案 D 验证
8. 回归与推荐
9. 人工"发布确认（Gate 3）"后发布
10. 问答验证 → 反馈 → 新一轮优化

## 2. 术语规范（全站统一）

**1. 保留英文的核心词**：Agent、RAG、Pipeline、Baseline、Judge、Candidate、Bad Case、Token、Chunk、API。
- 每页第一次出现时，用括注或可点开的说明给出中文含义；
- 大小写统一，例如"Bad Case"。

**2. 中文为主的词**：英文作为小字附在后面，或放进可点开的说明里。

| 英文 | 中文 |
|---|---|
| Golden Dataset | 黄金测试集 |
| Sandbox | 沙盒评测 |
| Winner | 优胜方案 |
| Hard Gate | 硬门槛 |
| Gate 1 / Gate 2 / Gate 3 | 题卷确认 / 报告确认 / 发布确认 |
| Probe | 检索探针 |
| QC | 质检 |
| Parent / Child | 父段落 / 知识片段 |
| Rerank | 重排 |
| candidate_k / top_k / min_score | 候选数 / 保留条数 / 最低相关分 |
| hybrid_alpha | 语义与关键词权重 |
| query_rewrite / multi_query / hyde / query_decompose | 问题改写 / 多问法检索 / 假设答案检索 / 问题拆解 |
| Strict / Looser / Safe | 严格 / 宽松 / 安全 |
| P50 / P99 | 延迟中位数 / 延迟高位 |
| correctness / faithfulness / completeness | 正确性 / 忠实度 / 完整性 |

页面上不出现 Coverage Plan、slot、cluster 这类内部词。

**3. 参数显示**：一律写成"中文名 + 等宽小字代码名 + 旧值→新值"，变化的部分加粗。

**4. 禁用字样**：Gate 1 相关页面不得出现"AI 确认""自动确认""代为确认""Codex""机器"（规则总表八.1）。

## 3. 结果展示的口径

**1. 判定只有两种**：正式 PASS 或正式 FAIL，不准新增第三种成绩或审核状态。
- 人工复核的发现，写成"独立审核备注"。例如 Q05 显示为"正式 PASS · 人工复核：回答含无依据表述"。
- 未修好的题写本轮事实。例如 Q15 写"本轮未修复：36 个月项目被误计入 12 个月"，**不要贴"表格理解限制"这种永久性的能力标签**。

**2. 每个方案分三层展示，不能只给一个绿色"合格"：**

| 层次 | 回答的问题 | 示例 |
|---|---|---|
| 正式资格 | 11 项硬门槛是否全过、新增严重错题是否为 0 | 合格 / 不合格 |
| 实验效果 | 相对 Baseline 修好几道、新错几道，答对多少 | 48/50，修好 3，新错 0 |
| 证据可信度 | 每道修好的题是"证据有变化""同型号其他来源"还是"只有结果变化"，有没有审核备注 | Q21、Q27 证据有变化；Q05 只有结果变化，有备注 |

**3. 状态依据**：Agent 的 KPI、推荐、发布状态都按真实状态显示。例如 D 还没跑时，显示"待报告确认（Gate 2）/ 待运行 D"，不准提前显示"最终推荐方案"。

## 4. 页面改造要点

1. **概览**
   - 4 张 KPI 卡，按故事线顺序排：知识库、黄金测试集、Baseline、Agent。数字全部绑定当前有效的知识库、冻结题卷、Baseline 和实验，并核对它们的版本身份是否一致；
   - 卡片下方放一行"当前进度"，例如"已完成第 1 轮，待报告确认"。
2. **各页页头**
   - 只保留一句话说明这一页负责什么；
   - "产出"和"下一步"根据页面上的实际内容动态显示，不要每页都塞固定的三行灰字。
3. **职责分清，不重复同一个结论**
   - Baseline 页负责诊断：错题和归因；
   - Agent 页负责优化假设和方案；
   - 沙盒评测和回归负责：收益、副作用、推荐依据。
4. **Agent 工作台**：在现有的 CandidateOverviewTable 和 CompareTable 上改造。
   - 桌面端并排显示 Baseline、A、B、C、D 五列。行包括：方案名和主攻层次、改了什么、三层结论、修好的题（题号标签）、新错的题、风险类题逐题对比（安全 5、注入 3、负向 20）、P50/P99；
   - 窄屏改为可切换方案的纵向卡片，表格只允许在自己的容器内横向滚动，整页不能横向溢出；
   - 错题流向：在 Regression 汇总里，按"题 × 方案"显示对或错；
   - 轮次时间线：沿用已有的 D 方案时间线，补上 Gate 2 节点和每一步的规则依据；
   - "说明书没有"话术计数：作为观察指标显示，Baseline 和各方案分别给出；
   - 原始 JSON 和日志一律收进"查看原始记录"抽屉。
5. **题号标签**：全站统一，点开后都是同一个题目抽屉，里面依次是：问题、参考答案、各次运行的回答、Judge 三维分、证据进入情况、审核备注。

## 5. UI 细节

1. **状态颜色统一**：绿色表示合格、对、修好；红色表示错、新错；灰色表示未运行。审核备注用中性色加图标，**不要用一种新的状态颜色**。
2. **小号浅色字只用于元数据**：ID、版本、指纹、路径、时间、代码名。关键的解释、状态和操作提示要保证可读，颜色对比度要达到 WCAG AA。
3. **重点内容加粗或放大**：答对数、门槛结果、结论、修好和新错的题号。
4. **对齐**：详情页用"标签：值"两栏，标签栏固定宽度；数字右对齐，用等宽数字；表头吸顶；同一页里卡片标题对齐。
5. **说明的展示方式**：重要说明直接显示在页面上；其他说明做成点击或键盘聚焦就能打开的形式，不能只支持鼠标悬停（手机和键盘要能用）。
6. **空状态**：写清楚为什么没有数据、下一步要做什么，例如"题卷冻结后显示"。

## 6. 已知遗留问题（101f 定稿的两项 P2，要在对外演示前关闭）

1. **"机械结构与密封件"组名不够准确**：组里有 5.2 通用程序、5.5.1、5.5.2，但"上臂和下臂"组里没有 5.5.1。改法：显示名按实际成员来写，例如"下臂、外壳与通用密封程序"，或者在组名下面列出成员。原来的组 ID 和数据关联都保留。
2. **配额 ≤2 的小主题**：第二层隐藏"目标配额"列，加一行小字"该主题第二层仅供浏览"。一级主题的真实配额和题卷统计照常保留。
