## 慢的原因与修改

1. **轻量题卷带了大审计。** `snapshot_summary()` 原先保留 `scoring_revision`，当前题卷的这部分约 2.19 MB。现在仅从轻量展示投影省去它；完整冻结题卷与数据库原文保留。来源：`backend/app/governance.py:snapshot_summary`；修改前接口字段大小抽查。
2. **重复下载同一份已完成评测。** 严格模式重挂载和多个组件会并发请求相同详情，实测单份约 10–18 MB；已完成详情以前每次重新下载。现在 `getJson` 合并同 URL 并发请求，最多保留 24 个已完成详情 30 秒；数据库版本头变化或成功写操作会失效。运行中记录、仍有运行中候选或循环的实验不进入完成记录缓存，轮询接口带 query 的请求也不会用此详情缓存。来源：`frontend/src/api.ts`、`api.test.ts`。
3. **方案抽屉提前下载折叠审计。** 修改前打开方案就拉约 18 MB 评测及约 34 MB 完整实验。现在打开主抽屉先用已有方案内容；展开“完整逐题报告与原始候选审计”或用量区时才取对应大记录。真实浏览器已核对展开后有 50 行逐题记录和 8,255,709 字符原始候选审计，宽度 798 px、正文无横向溢出。来源：`frontend/src/pages/EvolutionPage.tsx`、本机浏览器检查。
4. **同一快照重复 JSON.parse。** Agent 的多个题目 tooltip 原先每次解析同一份约 2.6 MB 快照。现在用 WeakMap 按对象及原始字符串复用解析值，Baseline 页面与 Agent 共用，题目原文不变。来源：`frontend/src/evaluationProgress.ts:savedSnapshot`、`components/EvolutionStory.tsx:questionText`；回归测试验证三次读取只解析一次。
5. **重复计算已经取回的同轮方案。** 实验展示为每个方案计算轮次完成度时，又重新读取同一批候选；现在复用本次已经加载的 peers，仍调用原来的轮次统计规则。来源：`backend/app/governance.py:experiment/round_completion/release_state`；测试对比新旧展示状态一致。
6. **后端重复生成和传输展示响应。** 新增仅 GET 展示接口的进程缓存，按数据库文件/WAL、索引 manifest、Corpus 状态和配置文件版本失效；最多 64 项且不超过 64 MiB、最长 30 秒。存在活动评测时绕过缓存；不缓存错误响应，Origin 与 query 分别隔离。空 WAL 的创建删除不算数据变更，已有回归测试。添加 gzip。来源：`backend/app/read_cache.py`、`backend/app/main.py`、`test_read_cache.py`。
7. **初次切换没有准备数据与模块。** 空闲一秒后逐页预取，导航悬停/聚焦也预取；按页拆分模块，首包构建产物 299.60 kB（gzip 101.14 kB）。首次等待时显示目的页面标题与骨架，替换整页转圈；题目详情悬停预取且重开先读缓存。来源：`frontend/src/App.tsx`、`pages/GovernancePage.tsx`、构建输出。
