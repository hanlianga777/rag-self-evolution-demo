## 根因

### 失败发生在 Judge 校验，源头是复用键遗漏来源身份

C 的配置只把混合检索语义权重改为 0.3。Q03 的最终 Parent 正文和 Baseline 相同，回答也可复用，但命中的 Child ID 集合不同：

- Baseline 的 Parent `DOC-001-V2-P-00011` 允许引用的 Child 包括 `DOC-001-V2-C-00054`。
- C 的该 Parent 只保留 `DOC-001-V2-C-00053` 作为 matched Child，没有 `00054`。
- 原 Judge 缓存键只使用 `generation_context()` 渲染文本，漏掉 `parent_chunk_id`、`matched_child_ids` 等引用绑定。这两个不同的判分输入因此得到同一个业务缓存键；这是键构造信息不完整，不是 SHA-256 算法碰撞。
- C 取回 Baseline 的合法旧判分，其中引用 `00054`。后端按 C 的实际 Final 再校验时正确拒绝。不能把旧引文改成另一个 ID 来强行通过。

缓存来源确认是 Baseline `EVAL-20261115170609095674`，旧缓存请求键 `62eab6565d905e236f89d545ca83a30b17ab0f62a951e6b65b20682e51244d9f`。三次 C Run 的 Q03 合计 24 次 Judge 阶段失败，usage 均为空：循环反复检查缓存，没有真的重新请求 Judge，也没有吞掉错误后形成业务成绩。
