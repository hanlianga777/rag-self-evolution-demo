# 人工停止与 Sandbox 续跑修复

用户本次直接授权：修复停止后的续跑、demo 运行弹窗的人工停止入口，以及“继续 Sandbox / 运行 Sandbox”无反应；然后恢复实验 `EXP-20261104150712113417`，不传 `current_round_only`。本次未执行旧的 013 任务单其他部分。

## 查到的原因和修改

1. **旧停止记录挡住新续跑。** `run-cycle` 虽返回 201，循环读到旧 A 的 `stop_request` 后立即又停下。现在只在用户明确启动新循环时，记录本次允许复用的旧停止 Run；通过原有身份与断点预检后创建子 Run。旧记录不删除、不改分；子 Run 如果再次被人工停止，仍会停下来。修改：`backend/app/optimization_cycle.py`。
2. **有三套合法方案，页面却不让运行。** 真实接口的第 2 轮 A/B/C 已保存，但覆盖规划为 5/6，Q38 尚无方案覆盖。原前端把所有覆盖不全都当作禁跑条件。现在三套已保存时可以试跑，仍显示覆盖缺口；方案没齐时仍先补齐规划。另取消“产品中断”状态一律禁用手动继续的逻辑；循环正在运行时仍禁止重复启动。修改：`frontend/src/pages/EvolutionPage.tsx`。
3. **循环运行弹窗缺少停止入口。** 新增 `POST /api/experiments/{id}/stop-cycle`。请求持久保存，停止活动 Sandbox，并阻止接下来预约 B/C/下一轮；等待平价和方案生成的请求边界同样检查停止请求。正在请求模型时，等待结果保存后停止，不丢弃已付费结果。修改：`main.py`、`optimization_cycle.py`、`optimization.py`、`paid_schedule.py`、`paid_policy.py`、`governance.py`。
4. **前端显示和恢复。** 单评测和循环的运行状态弹窗都提供“停止运行”；请求后显示“正在停止…”，错误会显示并可重试；真正停止后显示“已停止，断点已保存”，不再误显示完成。刷新页面也会恢复正在运行循环的停止入口；打开详情抽屉后按钮仍可操作。手动停止后复用同一次 Sandbox 预算。修改：`frontend/src/operation.tsx`、`backend/app/governance.py`。

不改 Golden、Baseline、判分合同、11 项门槛、Gate 2、D 或发布规则；Q38 的覆盖缺口保留。停止不是强杀 HTTP 请求，正在进行的请求会先返回并保存结果。
