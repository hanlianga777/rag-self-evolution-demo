# 56 跑题流程不中断：Claude 与 GPT 合议（2026-11-26）

Claude 独立审查见互审 55，GPT 的独立方案见 ChatGPT「Agent阶段风险审查」11-26 回复。两边结论高度一致。

## 一、共同结论

1. **直接原因有两个，都是 P0**：
   - E5 运行器主动关掉了传输重试（`run_e5_unattended.py:149-157,494-498`），导致一次 SSL EOF 就让整个运行停下；
   - 「生成诊断」被设成第 2 轮的强制前置，但普通编排入口里没有执行它的步骤，所以按钮路径一到第 2 轮就卡住。
2. **共同根因**：系统里没有一套统一的任务编排和恢复机制。现在有三条执行路径，各自维护一部分流程：
   - 前端「下一轮」按钮：`EvolutionPage.tsx:265` → `main.py:1870` → `OptimizationAgent.generate()`（这一条是 GPT 补充发现的）；
   - 前端「自动优化」：`main.py:2432` → `run_until_qualified()`；
   - E5 脚本：自己补做诊断、复测和发布。
3. **不能再「发现一个问题就写一个专用补丁脚本」**。Claude 昨晚写的 `run_e5_forever.sh` 属于临时措施，统一编排上线后删除。

## 二、根治方案（合并版）

1. **统一编排层 `app/workflow_engine.py`**：
   - 按钮、脚本、服务重启后的恢复，三种入口都调用同一套编排服务；
   - 用户仍然可以只跑 Baseline、只跑某个 Candidate、只跑本轮，或一路自动跑完，区别只在授权范围和目标阶段；
   - 生成诊断、最终复测、发布检查都迁进正式后端，由编排器自动执行前置步骤。
2. **统一重试，分两级**：
   - **请求级**：在 `providers.py` 一处处理 SSL、连接重置、DNS、408/429/5xx，按 5 秒、15 秒、30 秒间隔重试，429 优先遵守 Retry-After；
   - **任务级断点恢复**：间隔 1、2、5、10 分钟。持续故障时进入「等待恢复」状态，不判实验失败；超过等待期限再交给人处理；
   - 三层重试共用一个计数，避免次数相乘；
   - 重试过程中不得换模型、不得降 thinking 档位、不得改参数；
   - 记账不能成为关闭重试的理由：每次请求按「预留 → 发出 → 保存 → 结算」走，结果不确定的请求保守占用预算；
   - 续跑时读取同一份授权和剩余预算，切换入口不会重新获得一份预算。
3. **状态分离，加租约（心跳）**：
   - 业务状态拆成 queued、running、retry_wait、recovering、blocked、paused、completed、failed；
   - 进程占用另用「租约 + 心跳 + 执行令牌」表示；
   - 心跳超时的任务安全回收，从断点续跑；
   - 用户主动停止的指令要持久化，自动恢复不得把它重新启动；
   - `external_runner`、`claim_cycle`、候选 running 这些判断一律改走租约（Claude 列出的第 4、5、6 条）。
4. **只在必要时停下**：
   - 预算超限；
   - 知识库、题卷、Judge 身份不一致；
   - 规则校验连续被拒；
   - Provider 鉴权失败或余额不足；
   - 发布审批（用户已授权的情况除外）。

   停下时要写清楚原因和继续的方法。
5. **知识库、Golden、Probe/QC 也纳入断点续建**：
   - MinerU 解析（`knowledge_pipeline.py:1035-1068`）；
   - 切块和向量化（`knowledge_pipeline.py:1106-1199`）；
   - Corpus 切换（`corpus_management.py:20-54,76-174`）；
   - Golden 生成（`main.py:848-1015`）。
6. **故障注入回归**：
   - 模拟 SSL EOF、429、503；
   - Sandbox、Baseline、知识库重建都在中途 kill 进程后续跑；
   - 用按钮、脚本、服务重启三种入口，在隔离库加假 Provider 上把整套流程跑到发布，三者的结果、资格和费用一致。

   不为了测试真跑 E5。

## 三、Bad Case 优先级（问题第 4 点）

**采纳 GPT 的「四层故障 + 独立严重度」**，不照搬朋友的「故障类型 = 固定严重度」。理由：普通维修参数召回失败，不一定比遗漏危险操作的安全警告更严重；朋友说的「安全误伤」是过度拦截，和严重安全违规不是一回事。

- **四层**：检索、生成、安全、性能。
  - 现在的 `LAYERS` 只有三层（`agent_round_contract.py:12`），`layer_signals()` 还排除了延迟门槛（约第 240 行）。
  - 需要补上性能层的诊断证据和可选动作，例如 thinking 降档、减少多路查询、缩小 `candidate_k`。
- **严重度**：致命、严重、中等、轻微，由冻结的业务风险合同、实际错误和门槛结果决定，Agent 不能自己定。
- **新排序**：
  1. 严重安全违规；
  2. 导致 Hard Gate 失败的问题（含性能门槛）；
  3. 各层最高严重度；
  4. 同严重度下，错题多的层；
  5. 再相同时，按上游依赖排；
  6. 该层没有可调机会时，转到下一层。
- **新规则带来的能力**：50/50 全对但 P99 超标时，也会启动性能优化；性能改善但新增错题的方案不晋升。
