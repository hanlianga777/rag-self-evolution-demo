## 讲解逻辑（为什么这样改）
面试时进入 Agent 工作台，听众要在 10 秒内知道三件事：Agent 最后选出了什么、为什么可信、亮点在哪。然后再按轮次看过程。所以页签改成：

> **概览｜进化路线｜Candidate 对比｜回归与推荐**

- **页签位置**：直接放在页面标题下方，位置和样式与其他一级页面完全一致。

## 2. 新增「概览」页签（默认打开，用户第 26 条）
从上到下四块，数字全部从保存数据计算：

1. **结果卡**：
   - 左侧大字"推荐并已发布 Candidate D"，下面一行是答对 44 → 48、新增 Bad Case 0、Hard Gate 11/11；
   - 右侧是 3 轮、10 个 Candidate、评测预算 10 / 12。
2. **最终改动的 3 个参数**：三张同尺寸小卡，每张写：
   - 参数名和变化，例如"Candidate K　12 → 24"；
   - 一行灰字说明这个参数来自哪里，例如"R3-C 引入""R2-B 验证过、D 采纳"。

   来源从保存的 Candidate 参数和 D 的组合来源字段推出来，推不出的写"—"。
3. **Agent 的三条规则**（亮点）：三张卡，各一句完整长句，原样使用：
   - **三个方向互斥**：每一轮的三个 Candidate 必须改不同的参数，其中一个固定走"降档 + 检索补偿"的效率方向，这样结果变好或变坏都能说清是哪一处改动造成的。
   - **修好不能抵消弄坏**：只要新增了严重 Bad Case，或者普通 Bad Case 超过一个，修好再多题也不算合格，这就是"回归检查"守住的底线。
   - **事先预测，事后对账**：Candidate D 在评测之前就写下预计修好哪些题、要盯住哪些题，跑完以后逐条核对，没修好的也要说清原因。
4. **Bad Case 去向表**（用户第 30 条，替换原来折叠的"Agent 规划 · 逐题覆盖详情"）：
   - Baseline 的 6 个 Bad Case 每题一行，列为：题号、所在层、Agent 指派的方向或 Candidate、第一次被修好的 Candidate、最终状态（D 已修好 / 仍未修好）。
   - 讲解时一眼能看到"每个 Bad Case 都有人负责，最后修好 4 个、剩 2 个"。
   - 数据来自现有的 `processingCases` 和逐题结果。
   - 原来的折叠块和下方与之重复的信息删掉；只有表里放不下、又确有价值的，才放进点题后的抽屉。

**首屏**：1440×900 下尽量一屏。

## 3. 进化路线页签（用户第 27 条）
- **删掉**：最上面的 Baseline 一行（44/50、6 个 Bad Case、题号徽章、"查看 Bad Case 诊断""查看可调参数"）。Baseline 前面已经讲过了。
- **轮次切换**：
  - 不再一屏往下滚；顶部用按钮组切换"Round 1｜Round 2｜Round 3｜Candidate D"，样式与"Candidate 对比"页签的轮次按钮一致。
  - 默认 Round 1。
  - 删掉"查看轮次"这类前置标签文字（用户第 31 条）。
- **每一轮顶部**：一个**蓝框**的"本轮策略"块（`--ui-accent` 1.5px 边框、浅蓝底、14px 圆角），包含两句：
  - **本轮思路**：Agent 这一轮为什么选这三个方向。从保存的 Agent 推理原文中提取，可以压缩措辞，但不能加入原文没有的判断；
  - **本轮经验**：沿用 023 已有的完整句。
- **每张 Candidate 卡**：卡片上部加一个**蓝框**的"设计用意"块，一句话说明 Agent 为什么这样设计这个 Candidate。例如"沿用 R2-B 验证过的 Top-K 6，但这次只改这一项，用来单独确认它对安全拒答的影响"。
  - 来源同样只能是保存的 Agent 推理原文：思路、假设、依据、与前几轮的关系等字段，可以压缩，不能编。
  - 原文里确实没有"为什么"的，就只显示该 Candidate 的思路原文第一句。
  - 每张卡都摘了哪一段原文、怎么压缩的，列进报告，供总指挥核对。
- **卡片内其余字段**：参数变化、修好、新增 Bad Case、Hard Gate、答对与耗时，保持现状和对齐。
- **Candidate D 按钮**：内容由 027f 重构，本单只负责切换和容器。
