# 总指挥守则（2026-11-16 复盘后定，约束总指挥自己）

> 来源：`指挥/复盘/2026-11-16-根因复盘.md`。159 张任务单里反复付出的成本，多数来自总指挥这一侧：写了没跑、规则跟着单次结果改、花钱前没先确认"这次能不能看出效果"。下面每一条都对应一次真实的返工。

## 一、开跑三问（任何付费 Baseline / Agent 之前，必须先在报告或任务单里写出答案）

1. **信号有多大？** Agent 手里的参数能修好几道题？用 `backend/scripts/retrieval_headroom.py` 实测（只检索、几分钱、结果可重复），不靠估计。
2. **噪声有多大？** 同一配置跑两遍会有几道题对错不同？已知数据：11-15 实验里同配置重跑，50 题有 2–3 题翻转（R1-A↔R3-A 2 题，R1-B↔R2-C 3 题）。Judge 换档或换题卷后要重测。
3. **判据是什么？** 合格规则在开跑前写定，跑完不改。

信号不到噪声的 3 倍，就先想办法放大信号（改题卷），不要开跑，也不要事后改规则去"救"结果。

## 二、决策冻结

- Judge 档位、Baseline 档位、门槛、合格规则、题卷，**不因为某一次结果好坏而改**。要改，先写假设（"改成 X，预计 Y 会变成 Z"），用小样本验证，再换版本号。一个周期最多改一项。
- 反例：Judge 档位 low→off→low→off→low+3 次，五次变更里两次发生在同一天；Baseline 档位 high→max→off→max。

## 三、单一真相

- 影响运行的规则只有一份机读版本：`指挥/规则总表-机读.json`。改规则时，`规则总表.md` 和机读 JSON 同一个提交里改。
- 每张付费任务单的第一步是 `config_doctor.py`，不一致就停。
- 反例：规则写 Baseline = Max，`.env` 里一直是 off，直到人工翻配置才发现。

## 四、先跑后发（总指挥写的代码，自己先跑）

发任务单前，在自己的环境里至少做到：

1. `bash scripts/preflight_tests.sh`：和基准提交对比，**没有新增失败**才发。这个云端环境能跑 1000 多个后端测试，不要用"我这里跑不了"当理由。
2. 题卷类改动：`backend/scripts/golden_offline_check.py --csv … --chunks 指挥/报告/046-切块全量.csv` 必须 0 错。**验的必须是正式要跑的那个函数**，不能另写一套读法。
3. 改了字段、量纲、口径：在任务单里列出所有使用方（后端、质检、前端、测试）的文件名，逐个改到。
- 反例：049 前"本地验过 0 错"，验的是另写的 CSV 读法，正式脚本吃掉了单元格换行，19 题报错、两次暂缓；047 判分量纲改了，前端没跟。

## 五、任务单写法

- 第 1 步永远是便宜的冒烟检查（体检、dry-run、3 题小样），带硬停止条件。
- 硬停止触发 = 阻断完成，Codex 写报告并归档，不重试（`AGENTS.md` 第 11 条）。
- 验收写数字，不写"通过即可"。

## 六、先实质，后表现

- 演示用的实验结果没定下来之前，不发前端任务单（必要的显示错误修正除外）。
- 反例：159 张任务单里约 64 张是前端和展示；032 整体改版后整体退回；每次数据一变，页面要重查一遍。

## 七、对齐朋友的"机制"，不对齐"字段"

- 每个设计点都要能用一句话讲出"为什么这样设计"，面试官问的就是这个。"因为朋友这样做"不算理由。
- 朋友的核心机制只有一条：**题卷里专门放检索难的题 → Baseline 在消融指标上不过线 → Agent 调检索参数补回来 → 过线且不回退的方案胜出。** 先保证这条成立，其余字段是次要的。

## 八、一个仓库只有一个当班总指挥

- 同一时间只允许一个会话往 `指挥/队列/` 发单、往 main 推代码。其他会话的改动推到单独分支，由当班总指挥审核合并。
- 接手前先 `git log origin/main` 看最近 1 小时有没有别的会话提交；有就先对齐，不要各修各的。
- 反例：11-16 晚两个会话同时修 049 的 CSV 读法。
