# 页面性能与当前候选池整改验收 · 2026-10-25

基于已核对与 origin/main 同步的 `abddf8d`，使用 ponytail 最小整改。真实服务为 5174 / 8010，Chromium 真实渲染；不运行 Baseline、Agent、Sandbox、Probe 或 QC。Provider 调用 0，正式业务表写入 0。正式库重载前通过 SQLite Backup API 备份到 `backend/data/audit_backups/page-performance-20261025.db`；每次重载先检查无活动评测/候选/Golden任务。

## 三个主要根因

1. `App.tsx` 的 `loadedPage !== page` 分支在每次导航时替换整个 App，侧栏随整页 Loading 消失，页数据被替换而不能快速复用。改为八页进程内快照、常驻侧栏及内容区加载；每次进入、窗口聚焦、操作结束向后台重验，身份变化清除其他页缓存，旧请求不覆盖新页。没有加入状态管理框架或永久缓存。
2. 轻量接口仍携完整快照、重复 `_json` 字符串、Checkpoint、Recommendation 比较与候选诊断审计；Agent 与 Bad Case 接口分别重复计算相同诊断。Baseline 挂载即取完整逐题记录，Golden 初始化取全部完整 Snapshot。改为摘要/详情读取分离、Agent 复用同次诊断，保留完整详情入口。初始化不带完整 Trace 或 Judge 原始响应；打开单题详情才读取完整证据和冻结快照。GET 15 秒超时显示错误/重试，不修改 Provider 的技术时限。
3. 候选池把 225 道历史题做谱系合并后得到 86 道，混合多个工作版本；摘要另有 50 次逐题读取及历史全量解析，Case 成员查询没有 run_id 索引。改为当前有效工作 Run 的持久化成员、批量摘要 SQL、Case 覆盖索引。历史数据不删除，组卷材料池的有效谱系逻辑继续保留。

## SQL、数据量及重复执行开销

- 整改前只读 cProfile：Baseline 身份解析约 131 ms / 5 查询；Dataset 摘要约 82 ms / 64 查询；历史候选谱系扫描约 239 ms / 4 查询，读取 225 题后合并为 86 题。正式数据没有锁定为不可读。
- 整改后：摘要约 43 ms / 3 查询；当前工作候选约 147 ms / 5 查询，仅对 50 个成员计算资格。历史组卷的谱系函数仍然存在，只有组卷材料选择会使用它。
- 新增 `evaluation_case_run_question(run_id,question_id)`，实际 EXPLAIN 为覆盖索引 SEARCH；10 次、SQLite busy_timeout=0 的成员查询中位数约 0.019 ms，未观察到 busy/locked。此结果不证明其他时段不存在锁等待。
- 概览、Baseline 轻量正文明显缩小；历史 225 题引起的开销是上述百毫秒级读取，不能解释成“50题太多”或直接归因为电脑性能。真实诊断计算仍占约 1 秒。
- 点击 Golden 详情原来冒泡触发行和按钮两次读取；复现测试先失败（2 次），修复后 1 次。详情材料在 StrictMode 下原来重复请求，微任务与卸载取消后只读 1 次。保留 StrictMode，没有用关闭诊断能力掩盖重复执行。
- 上述为各路径观测与阶段对比，存在共同 CPU/文件读取成本，不能简单相加为独立的因果耗时。
